4 · Las dos causas concretas en el código

4.1 · Singularidad 1/f que quedó SIN arreglar — backward.cu:485

float d_alpha_d_rho = alpha * beta_j * df_drho / f_safe;   // f_safe = max(f, 1e-6)

Con el kernel viejo f = 1−ρ esto solo tocaba f→0 justo en el borde ρ=1, que el guard if (r2 >= 1.0f) continue; excluye. Con la base Gabor f(r) cruza cero DENTRO de la huella. Medido sobre el ply de 30k (muestra de 400 K splats):

Forma aprendida (ply @30k)

  • 67,0 % de los splats tienen f(r)<0 en algún r<1
  • radio de corte f=0: p10 = 0,60 (med 1,00)
  • 35 % tienen lóbulo real (g>1 fuera del centro), g_max hasta 2,47
  • r½ del kernel: med 0,205 (la tent β=1 daría 0,5) → kernels mucho más picudos
  • β sano: min 0,0986 · med 2,73 · mean 2,91 (sin trinquete)
  • Σaₙ = 0,5000 exacto ⇒ la proyección estaba activa y funcionando

Alrededor de ese cruce hay un anillo entero de píxeles con f≈0. Y para β<1 (β min medido = 0,0986):

α / f = opa · gβ / f = opa · fβ−1 / f₀β  →  con β=0,1 y f en el piso 1e−6: ×105,4

Eso son factores de 1e5–1e6, que es exactamente el orden de los máximos del log (2,4e3 → 2,6e6).

Lo llamativo: el propio commit d5242ea ya aplicó esta corrección al gradiente de aₙ (reagrupar a opa·β·g^(β−1)·(cₙ−g)/f₀ para no dividir por f, con piso solo si β<1)… pero no la aplicó a d_alpha_d_rho, que es justo el que alimenta dL_dmean2D → el criterio de densificación del clásico. Además el gate if (beta_j >= 0.1f) protege los gradientes de β y de a, pero no el de ρ, que es el singular.

4.2 · Quitar la proyección Σaₙ=0.5 abrió una SEGUNDA singularidad

El argumento del commit — "el rasterizer ya normaliza por f₀, así que Σaₙ es libre" — solo vale si f₀ > 0. Ahora f₀ = ½ + Σaₙ es un parámetro libre que aparece como denominador en dos sitios:

float f0      = 0.5f + a1 + a2 + a3;
float f0_safe = fmaxf(f0, 1e-6f);
float g       = fmaxf(f_safe / f0_safe, 1e-6f);        // forward.cu y backward.cu
float a_coef  = dL_dalpha * opa * beta_j * g_pow / f0_safe;   // backward.cu:468

Nada impide que f₀ → 0 o se vuelva negativo. En cuanto pasa: f0_safe = 1e-6 → g = f·10⁶ → kernel y gradientes disparados, y el splat se convierte en un disco de opacidad saturada. Eso explica que el relanzamiento de hoy llegara a 52 M en la iteración 4.100 cuando el de ayer, con la proyección activa (Σa = 0,5000 exacto verificado en el ply), tardó 30.000 iteraciones en llegar a 22,5 M.

Como load_ply deja spatial_lr_scale = 0, el guard de get_scaling (gaussian_model.py:139) no clampa al renderizar: esos splats se pintan hasta 9× más grandes que durante el entrenamiento. Es la inconsistencia train↔render ya conocida de run64/run65, aquí amplificada ×8. Parte del destrozo visible (y del 14,76) es ese artefacto de render, no el modelo entrenado — así que ni siquiera el 14,76 es una medida limpia del kernel.

5 · Qué NO fue

  • No fue el trinquete de β: β min 0,0986, med 2,73, solo 0,032 % con β<0,1. El fix de run67 sigue vivo.
  • No fue el techo de β: 0,024 % topados en 29,5562 — igual que run67/72/74 (refutado ya en techo_beta_clamp_superior.html).
  • No fue una vista rota: el peor PSNR por vista es 13,02 y el mejor 16,89 → el fallo es global y uniforme.
  • No fue la forma del kernel en sí: los perfiles aprendidos son plausibles (picudos, con lóbulos en el 35 %), no degenerados tipo caja. El problema es el gradiente, no la forma.

6 · Plan recomendado

  1. Arreglar d_alpha_d_rho (backward.cu:485) con el mismo reagrupamiento que ya se hizo para grad_a:
    ∂α/∂ρ = opa · β · gβ−1 · f′(r) / (2r · f₀)
    sin dividir por f, con piso sobre g solo si β<1. Es una línea y es la causa más probable del reventón. requiere recompilar el rasterizer
  2. Revertir la eliminación de la proyección Σaₙ=0.5 (o garantizar f₀ ≥ ε de otro modo) hasta tener un run estable. Ahora mismo es un cañón sin seguro: el argumento de autonormalización se rompe en cuanto f₀ se acerca a 0.
  3. NO probar Gabor en CLÁSICO. El clásico densifica dirigido por ‖∂L/∂μ₂D‖, que es exactamente la magnitud que este kernel infla → es el peor banco de pruebas posible, y encima sin cap_max que acote la memoria. El primer run real debe ser MCMC con cap 7,5 M comparando contra run36 (21,16/0,5926/0,3555): el cap hace el run inmune a la explosión de clonado y acota la VRAM. El clásico, después, si el MCMC sale sano.
  4. Smoke test local de ~2.500 iters mirando el histograma de grad_pos (percentiles, no el máximo — regla del proyecto) antes de gastar Blackwell. Criterio de aprobado: mean y med del mismo orden y %≥thr de un dígito.
  5. Opcional pero barato: arreglar el clamp de escala en render (fijar spatial_lr_scale en load_ply) para que metrics.py mida el modelo que se entrenó y no discos 9× más grandes.
Coste de lo ya gastado: un run completo de 30k (5,5 GB de ply, 22,5 M splats) + un crash de 8 minutos. La salida output/m360/flowers_beta_run1 ya tiene todos los datos extraídos en este documento → borrable salvo que se quiera conservar el render de los anillos como evidencia visual.
